# Делать

## Словарь постобработки

Самое ценное из оставшегося: по августовскому замеру словарь снимает
**6,1 п.п. WER** — больше, чем дала бы смена движка. Проблема не в обычной
русской речи, а в рабочих терминах, и ошибки стабильны: `Dricks`/`дата брикс`
вместо `Databricks`, `GM 380 3` вместо `GM-383`, `Google Shits` вместо
`Google Sheets`, `слаг` вместо `Slack`.

**Ключевой принцип: не пары «ошибка → исправление», а список правильных
терминов.** Модель коверкает по-разному каждый раз, перечислять варианты
бесполезно. Вместо этого:

1. **Фонетическое притягивание.** Список из одних правильных терминов
   (30–50 слов: сервисы, префиксы задач, имена). Постобработчик находит в
   распознанном тексте слова, фонетически близкие к термину (Левенштейн на
   фонетическом представлении, с учётом транслитерации ru/en), и заменяет.
   `дата брикс`, `датабрикс` и `Dricks` ложатся на `Databricks` одной
   строчкой списка. Порог близости консервативный: ложная замена хуже
   пропущенной.
2. **Правила-шаблоны для структурного.** Номера задач, суммы, версии — это
   не словарь, а регулярки: «`GM` + пробелы/мусор + цифры → `GM-цифры`»
   чинит все номера сразу. Таких правил нужно ~5.
3. **Список терминов не составлять руками** — вытащить частотные термины
   из заметок второго мозга (SBvault) и истории диктовок. Пополнение — одна
   строка на новый термин.

**Где живёт.** В воркере, после `распознать()`: микросекунды на фразу,
задержки не добавляет. Отдельный модуль со своими тестами.

**Как проверять.** На трёх эталонных записях в `~/Chirper-замеры` через
`замер_точности.py сравнить` — цифра до/после. База без словаря: 21,3%.
Ожидание: минус ~6 п.п. Обязательно смотреть и на ложные замены: WER может
спрятать случай, когда словарь «починил» правильное слово.

**Потом, если захочется большего:** прогон текста через маленькую локальную
LLM со списком терминов в промпте — правит по контексту, но +0,5–1 с
задержки и новая зависимость. Начинать не с этого.

## Конвейер распознавания во время записи

Сейчас распознавание начинается после «стоп»: минутная диктовка ждёт ~2 с.
Куски по 20 с можно распознавать, пока человек ещё говорит, — после «стоп»
останется только хвост, задержка перестанет расти с длиной записи.

Цена — переделка протокола воркера и записи в Swift (буфер кусками вместо
одного файла). Стал актуальнее после режима фиксации: длинные диктовки
теперь удобно наговаривать, пусть будут и быстрыми. Сюда же — индикация
прогресса распознавания многоминутной записи (сейчас похоже на зависание).

# Проверить жизнью

Кода не требуют — нужно просто пользоваться и замечать.

## Режим фиксации

- Порог двойного нажатия 0,35 с ([`tapThreshold`](native/Chirper.swift#L1526)):
  не ловятся ли случайные фиксации при быстрой диктовке подряд и не слишком
  ли туго попадать в двойное нажатие. Подстройка — одна константа.
- Одиночный случайный тап теперь молча отменяет запись (раньше её отсеивал
  порог длительности) — убедиться, что сверхкороткие намеренные диктовки
  («да») не пропадают. Граница: удержание короче 0,35 с.
- Предел зафиксированной записи — 10 минут
  ([`lockedRecordingLimit`](native/Chirper.swift#L1528)), по истечении запись
  сама уходит в распознавание. Достаточно ли/не мало ли.

## После перехода на ONNX

- Задержка после долгого простоя и после сна: по замерам должна была
  практически исчезнуть (возврат ~330 МБ из swap — доли секунды).
- Если за неделю-две ни одна первая диктовка не покажется медленной —
  прогрев при старте записи ([Chirper.swift:1707](native/Chirper.swift#L1707))
  можно убирать как лишнюю деталь (страховка, оставленная сознательно).
  Прогрев при старте демона не трогать: он закрывает ленивую инициализацию
  onnxruntime.

## Плавающий баг: переброс фокуса при двойном нажатии

Один раз наблюдалось: двойное нажатие фиксирует запись корректно, но фокус
уходит в другое окно. Больше не воспроизводится.

**Что исключено:** вставка (синтез Cmd+V, не активирует), оверлей
(неактивирующая панель), Karabiner/Raycast/AltTab/Wispr (не запущены).
**Что не исключено:** сторонний обработчик двойного Option (проверка
синтетическими нажатиями не удалась — нет прав Accessibility у терминала),
случайное совпадение с чужим диалогом/уведомлением.

Если повторится: запомнить время и какое приложение оказалось в фокусе — по
этому можно понять, чей это обработчик. Постоянную ловушку не держим
сознательно (лишний фоновый процесс).

# Отложено

## Замер: поведение при выходе из сна

Попытка 2026-08-08 не удалась: система не заснула — `Yandex` держал
`NoDisplaySleepAssertion "Video Wake Lock"` (видео на странице). Признак
несостоявшегося сна: в логе RSS-сборщика нет разрывов во времени.

**Как повторить.** Проверить `pmset -g assertions` и закрыть вкладки с
видео → запустить сборщик RSS воркера (раз в 2 с, только чтение `ps`) →
`pmset sleepnow` или крышка, 15+ минут → разбудить, сразу продиктовать → в
логе искать разрыв во времени, смотреть RSS и скорость возврата.

**Что проверяем.** Глубину вытеснения после сна (`hibernatemode 3` сбрасывает
память на диск); не перезапускается ли воркер; работает ли микрофон сразу
после пробуждения. После перехода на ONNX (воркер 327 МБ, старт ~1 с) вопрос
менее острый, но «не всегда вставляется» после крышки может объясняться
именно микрофоном.

**Связанное отложенное решение — прогрев по пробуждению:** подписка на
`NSWorkspace.didWakeNotification` + `warmup` (команда в воркере уже есть).
Делать только если замер покажет, что после сна всё ещё заметна задержка.

## Подпись и нотарификация

Сборка подписана ad-hoc (`codesign --sign -`), поэтому у любого другого
человека macOS блокирует первый запуск: на macOS 15+ нужно идти в
**Privacy & Security → Open Anyway**, на 13–14 хватает «Открыть» из
контекстного меню.

Для раздачи паре человек это терпимо (инструкция есть в README и в описании
релиза). Снять ограничение можно только через Apple Developer Program —
99 $/год, подпись Developer ID и нотарификация (`notarytool submit` +
`stapler staple`) в [собрать_app.sh](собрать_app.sh) после `codesign`.
Делать, если приложение понадобится раздавать шире.
